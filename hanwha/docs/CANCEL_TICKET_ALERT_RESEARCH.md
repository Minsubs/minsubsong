## 1. 요약

- **자체 수집(서버 폴링/스크래핑) 기반 "잔여석 상태 변화 감지"는 5개 예매처 전부에서 불가하다.** robots/약관/안티봇 인프라 중 최소 한 겹 이상이 막고 있고, 무단 수집은 민사 패소가 입증된 경로다(야놀자 10억, 잡코리아 4.5억).
- 합법 데이터 경로는 좁다: ① 예매처/구단과의 **B2B 제휴 피드**(공개 셀프서브 채널 없음, 개별 협상 필요), ② **사용자가 직접 여는 명시적 확인**(공식 예매처 딥링크 + 시간 트리거 리마인더), ③ 예매처 **공식 취소표 대기 기능**(인터파크 예매대기, 티켓링크 취소표 대기)으로의 안내.
- 인터파크·티켓링크는 취소표 알림을 **이미 1차 사업자 공식 기능으로 운영 중**이므로, 본 제품은 감시 대행이 아니라 "관심 경기 저장 → 공식 대기 서비스 안내 + 공식 딥링크 + 시간대 리마인더"라는 **메타 레이어(컨시어지)**로 포지셔닝하는 것이 컴플라이언스와 차별화 양면에서 유리하다.
- PROGRESS.md의 1차 MVP 항목 중 "상태 변화가 확인된 경우 알림"은 현재 합법 데이터 소스가 없어 **제휴 성사 전까지 구현 불가**로 분류한다. 나머지(관심 경기 저장, 수요 신호 기록, 예매처별 지원 상태 표기)는 지금 가능하다.

### 2.5 롯데 자이언츠 — 불가

자동 감시 기준 3중 차단으로, 5개 중 유일하게 **불가** 판정.

- **인프라**: robots.txt 요청조차 `ntrafficCheck1.html`("LOTTE GIANTS 과도한 호출페이지")로 307 리다이렉트. 비브라우저 접근은 "비정상적인 접근으로 차단되었습니다" 페이지 반환 — robots 확인 자체가 불가(2026-06-11 curl 확인).
- **약관**: 제24조 3항 — "허용된 접근 범위를 초과하여 이용하거나, 비정상적인 구매(매크로 등 프로그램 이용, 반복적인 구매/취소 등)…" 금지. 제10조 — 서비스로 얻은 정보의 무단 복제·상업적 이용, 역설계 금지.
- **공식 API / 공개 상태값 / 제휴 프로그램**: 모두 없음. 예매 진입점이 로그인 폼이고 전 도메인이 트래픽 게이트 뒤에 있어 비로그인 공개 상태값이 사실상 없음.
- 가능한 것은 예매 오픈 일정 안내 + 공식 딥링크뿐이며, 그 이상은 구단 또는 판매 대행 대홍기획과의 별도 계약 성사 시에만 재검토.

### 3.2 크롤링 판례 — "형사 무죄 ≠ 민사 면책"

## 5. 가능한 접근 방식 비교

| 접근 | 합법성 | 구현 난이도 | 백엔드 | 효용 |
| --- | --- | --- | --- | --- |
| ① 제휴/공식 API | 계약 성사 시 완전 합법 | 높음 (BD 협상 + 연동 개발) | 필요 | 최상 — 유일한 "실데이터 상태 알림" 경로 |
| ② 사용자 주도 확인 (딥링크 + 리마인더) | 합법 — 표준 하이퍼링크 + 로컬 알림 | 낮음 (현행 구현 연장) | 불필요* | 중 — 상태 보장 없는 확인 유도, 수요 검증에 충분 |
| ③ 브라우저 확장 (사용자 세션) | 조건부 — 열람/링크 수준만 | 중 | 불필요 | 낮음 — 리스크 대비 효용 낮아 보류 권장 |
| ④ 서버 폴링 스크래핑 | **금지 — 제품 원칙 위반** | — | — | 채택 불가 |

- **① 제휴/공식 API**: 티켓링크 파트너 연동 API, SSG 쓱파트너스, NC 구단 직영 창구 등 협상 경로는 실재한다. 단 공개 프로그램이 없어 성사 가능성·기간 불확실 — 수요 검증 트래픽/전환 데이터를 레버리지로 쓰는 중장기 카드.
- **② 사용자 주도 확인**: 관심 경기 저장 → (a) 해당 경기의 공식 예매 페이지/취소표 대기 신청 페이지로 원클릭 딥링크, (b) 취소표가 잘 풀리는 공개 시간대(예: 자정 직후, 경기 전날) 기반 시간 트리거 리마인더. 잔여석 데이터가 전혀 필요 없어 제품 원칙과 완전 합치. *단, 앱이 닫혀 있을 때 알림 도달은 현행 구현(로컬 알림, `script.js`의 `showNotification`만 사용, `service-worker.js`에 push 핸들러 없음)으로 불가 — 진짜 Web Push는 VAPID + 구독 저장 + 발송 서버(또는 서버리스/푸시 SaaS)가 선결 과제이고, iOS는 16.4+ 홈화면 설치 PWA에서만 가능. (https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/, https://www.magicbell.com/blog/using-push-notifications-in-pwas)
- **③ 브라우저 확장**: Chrome Web Store 정책상 "웹사이트 콘텐츠 무단 접근 촉진" 제품 금지. 사용자 자신의 세션에서 페이지를 여는 수준은 명시적 금지 대상이 아니지만, 자동화·우회 기능이 한 줄이라도 들어가면 계정 해지 + 국내법 형사 리스크로 비대칭적으로 위험. 로드맵 보류. (https://developer.chrome.com/docs/webstore/program-policies/malicious-and-prohibited)
- **④ 서버 폴링 스크래핑**: **제품 원칙상 금지.** robots/약관/안티봇과 정면 충돌하고, 민사 배상 판례가 확립된 경로이며, 보호조치 우회 시 정통망법 침입 리스크. 검토 대상에서 영구 제외하고 "금지됨"으로만 기록한다.

## 6. 권고

### 지금 가능한 것 (제휴 불요, 현행 원칙 합치)

1. **취소표 컨시어지 v1**: 관심 경기 저장 → 예매처별 지원 상태 표기(본 문서의 판정 반영) → 공식 취소표 대기 서비스(인터파크 예매대기/티켓링크 취소표 대기) 신청 안내 + 공식 예매처 원클릭 딥링크.
2. **시간 트리거 리마인더**: 실데이터 감시 없이 공개 패턴(취소 마감시간대 등) 기반 확인 유도 알림. 현행 로컬 알림 구현으로 가능.
3. **수요 신호 기록**: 관심 경기 저장 수·딥링크 클릭을 `검증` 탭 신호에 추가 — 제휴 협상 레버리지 데이터로 축적.
4. **UX 카피 명시**: 기존 "예매 오픈 시각 알림"(공개 공지 기반)과 "취소표 알림"(상태 보장 없는 확인 유도)의 데이터 등급 차이를 분명히 해 사용자 기대 갭으로 인한 신뢰 손상을 예방.

### 제휴 성사 시 가능한 것

- 예매처/구단 제휴 피드 기반 실제 "상태 변화 확인 시 알림" (PROGRESS.md 1차 MVP의 마지막 항목). 우선 접촉 후보: NHN링크(파트너 API 실재), SSG(운영 주체 단일·창구 구조화), NC(직영·의사결정 단순). 선결: Web Push 백엔드(VAPID) 투자 — 수요 신호가 충분할 때 결정.

### 하지 않을 것

- 서버 폴링/무단 스크래핑 기반 잔여석 감시 (전 예매처).
- 비공개 내부 엔드포인트 리버싱·호출 (인터파크 `/v1/` 등).
- 로그인 대행, 자동예매, 대기열/CAPTCHA/안티봇 우회.
- 자동화 기능이 포함된 브라우저 확장.
- 롯데 자이언츠 대상 일체의 자동 접근 — 별도 계약 전까지 "오픈 일정 + 딥링크"만.

### 보류 조건 재확인 (PROGRESS.md와 일치)

> 예매처가 자동 조회를 금지하거나 로그인/대기열/안티봇 우회가 필요하면 해당 예매처는 지원하지 않는다.

본 조사 결과 **5개 예매처 전부가 현재 이 보류 조건에 해당**한다(자동 조회 기준). 따라서 Phase 3의 "상태 변화 알림"은 제휴 전까지 전 예매처 보류, 컨시어지형 v1만 진행 가능하다.
