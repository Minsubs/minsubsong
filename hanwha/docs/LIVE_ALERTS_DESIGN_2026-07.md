## 2. 아키텍처 — 3단계 (LV0 → LV1 → LV2)

```
[KBO 스코어보드]
      │ ①분단위/온디맨드 fetch (경기 시간대만)
      ▼
[Cloudflare Worker (X0 워커 확장)]
  GET /api/live ── 캐시 TTL 20~30s ──► [클라: 홈 패널 30~60s 폴링]   ← LV1
  scheduled() ─ live_state diff ─► 전이 이벤트(시작/득점/종료)
      │                                                              ← LV2
      ▼ Web Push (<CODE>:game_live)
[앱 닫힌 기기]                          [앱 열린 기기: 폴링 diff → 로컬 알림] ← LV1
```

### LV0 — 소스 PoC (선결, S) — ✅ 완료 (2026-07-10 실측)

**실측 결과 (설계 수정 반영됨):**
- **소스 판정: HTML 파싱(현행 parseScoreboard) 유지가 유일 경로.** 라이브용 JSON 엔드포인트 없음(스코어보드 날짜 이동은 ASP.NET 포스트백). CORS 헤더 없음 → 워커 프록시 필수(LV1a 방향 타당). **`/ws/` 경로는 robots.txt 전체 차단** — 라이브 소스로 `/ws/*` 확장 금지. ⚠️ 기존 `GetScheduleList`(`/ws/Schedule.asmx`)도 이 경계에 있음 — **D8 검토 항목에 추가**.
- **상태 문자열 실측**: 경기 전 = 시작시각 문자열(`"18:30"`), 종료 = `"FINAL"`. ~~진행중 표기는 올스타 브레이크로 실측 불가~~ → **(2026-07-16 실측 확정) 진행중 = `"TOP n"` / `"BOT n"`** (20:06~20:40 KST 3회 캡처, TOP 5~8·BOT 5~7 관측 — `.omo/evidence/live-scoreboard-20260716/`). 클라 표기 로직은 미인식 문자열을 그대로 노출하는 방어적 설계 유지(인식 문자열은 "n회 초/말"로 한글화).
- **🔴 취소/지연 상태 문자열은 존재하지 않음**: 우천취소·서스펜디드 실사례 3건 모두 스코어보드에서 해당 경기 블록이 **통째로 사라짐**(cancel/rain/suspend 문자열 0건). → LV2 `canceled` 감지는 상태 매칭이 아니라 **"일정(스케줄)에 있던 경기가 시작 예정 시각 이후에도 스코어보드에 미출현/중도 소실" diff** 로 판정한다(아래 LV2 절 수정 반영). `delayed`는 진행중 표기 실측 후 재설계.
- 영문판은 `?searchDate=YYYY-MM-DD` GET 지원(과거/미래 조회 가능). "경기 없음" 날은 games 0건 → idle 캐시(10분) 경로 필수(올스타전은 스코어보드에 안 뜸 — 별도 사이트).
- 갱신 힌트 없음(meta refresh/interval 전무) — 실시간성은 재요청 주기에만 의존, 분단위 cron 설정 타당.

원 조사 항목(참고용):

- `Scoreboard.aspx` 응답을 경기 중 시간대에 실측: 상태 문자열의 이닝 표기 형식(예: "6회말"/"Bottom 6"), 갱신 지연(경기 이벤트 대비 몇 초/분 늦는지), 응답 크기.
- **취소/지연 상태 문자열 실측**: 우천취소·중단(지연)·서스펜디드가 스코어보드 `state`와 일정 페이지 중 어디에, 어떤 표기로 뜨는지 + 취소 공지가 반영되는 시각(경기 몇 시간 전) 확인 — LV2 `canceled`/`delayed` 이벤트의 선결.
- `koreabaseball.com/ws/*.asmx` 계열에 스코어보드 **JSON 엔드포인트** 존재 여부 조사(이미 `GetScheduleList` 사용 중 — 같은 계열에 라이브용이 있으면 HTML 파싱 제거 가능).
- robots.txt/약관 확인 + 폴링 상한 결정. 원칙: **경기 시간대만, 워커 단일 지점에서 분당 1회** — 브라우저 1명 수준 이하 트래픽. (안전 원칙의 "무단 스크래핑 금지"는 취소표 감시 맥락 — 공개 스코어 표시는 기존 파이프라인과 동일 소스·관행의 연장. D8 검토 항목에 포함.)
- 산출: 소스 확정 + 파싱 함수 워커 포팅 가능성 판정.

### LV1 — 홈 실시간화 + 앱 열림 알림 (X0 배포 선결, M) — ✅ 코드 완료 (LV1a 2026-07-10 · LV1b 2026-07-16, `PUSH_API_BASE` 주입 전까지 게이트로 비활성)

**워커** (`worker/` 확장):
- `GET /api/live` 라우트 신설. 온디맨드 fetch + **캐시 TTL 20~30s**(동시 사용자가 몇 명이든 KBO 원 소스에는 TTL당 1회만 나감). `parseScoreboard`를 `worker/lib/scoreboard.js` 순수 함수로 포팅(단위 테스트 동반 — 기존 68개 스위트에 추가).
- 경기 시간대 밖(오늘 경기 없음/전 경기 종료)이면 `{games:[], idle:true}` + 긴 캐시(10분) — 무의미한 원 소스 fetch 방지.
- 무료 한도: 폴링 30s 기준 사용자 150명 동시 관전 시 ~90k req/일로 100k 한도 근접 → **클라 폴링 45~60s 권장 + 사용자 증가 시 하향 조정** (§5 결정 DL3).

**클라** (`script.js`):
- 홈 뷰 활성 + `document.visibilityState === "visible"` + 오늘 경기 존재 + 경기 창(첫 경기 시작 −10분 ~ 전 경기 종료) 조건에서만 `/api/live` 폴링. 뷰 이탈/백그라운드 전환 시 즉시 중단(Page Visibility API).
- 기존 `#liveGamePanel` 렌더러에 폴링 결과 주입 — **이닝·스코어·상태 배지(경기 전/N회 초·말/종료)** 갱신. `PUSH_API_BASE` 미설정(X0 미배포)이면 현행 정적 동작 유지(게이트 — X0 클라 셸과 동일 패턴).
- **앱 열림 알림**: 연속 폴링 결과를 diff → 마이팀 경기의 (a)시작(예정→진행) (b)마이팀 득점(마이팀 점수 증가) (c)종료(진행→종료) 전이 시 로컬 알림(`showTicketNotification` 패턴) + 인앱 토스트. 알림센터에 `경기 알림` 카테고리 토글 신설(**기본 OFF**, KISA 내용특정형 카피: "내 구단 경기 시작·득점·종료 알림").

### LV2 — 앱 닫힘 푸시 (X0 + LV1 후, M) — ✅ 코드 완료 (F4 2026-07-10 · `delayed` 2026-07-16, X0 실배포·실기기 검증 대기)

- 워커 `scheduled()`(이미 분단위)에 라이브 모니터 단계 추가: 오늘 경기 창에서만 `/api/live`와 동일 소스 fetch → D1 `live_state` 테이블(신규: `game_id PK, home_score, away_score, status, updated_at`)과 비교 → 전이 이벤트 산출.
- **이벤트 종류 5개**: `start`(예정→진행) · `score`(점수 증가) · `end`(진행→종료) · **`canceled`(우천 등 취소)** · **`delayed`(우천 지연/중단)**.
  - **(LV0 실측 반영) 취소 감지 = diff 방식**: 스코어보드에 취소 상태 문자열이 존재하지 않음(취소 경기는 목록에서 사라짐). 판정: 오늘 일정에 있던 경기가 (a)시작 예정 시각 +유예(예: 20분) 이후에도 스코어보드 미출현, 또는 (b)진행 중 표시되다 FINAL 없이 소실 → `canceled` 추정. 오탐 방지로 연속 2회(2분) 확인 후 발송.
  - **(2026-07-16 구현 완료) `delayed` = 2경로 diff**: 지연 전용 상태 문자열도 존재하지 않으므로 — **A(시작 지연)**: 블록이 스코어보드에 **잔존**한 채 pre 상태로 시작예정+20분 경과(취소는 블록 소실이라는 실측이 판별 근거) / **B(진행 중단)**: live 상태에서 state(하프이닝)·점수가 45분 동결(`live_state.last_change_at`로 추적). A/B 합산 경기당 1회 캡(`live:<key>:delayed`). 블록이 소실되는 서스펜디드는 기존 canceled 경로로 잡히는 한계 있음(문구 오분류 가능 — 백로그).
  - **모니터 창 확장**: 우천취소는 경기 시작 ~3시간 전(관행상 오후 3~4시) 공지되므로(ROADMAP X4 근거), 취소 감지 창은 **첫 경기 5시간 전 ~ 전 경기 종료**. 경기 전 구간은 5분에 1회만 확인(분초 안 다툼 — 원 소스 부하 절약), 경기 중 구간은 매분.
  - `delayed`는 상태 플래핑(중단↔재개 반복) 가능 → **경기당 1회만**(dedup), 재개 알림은 백로그.
- 토픽: **`<CODE>:game_live`** 단일 카테고리(이벤트는 페이로드 `event` 필드로 구분). 발송 대상:
  - 시작/종료/**취소/지연** → 홈·원정 양 팀 구독자 (취소는 원정팀 팬의 "갈까말까" 가치가 더 큼).
  - 득점 → **점수가 오른 팀 구독자만** (요구가 "득점 시"이므로. 실점 알림은 옵션 백로그).
- 중복 방지 dedup_key: `<gameId>:start` / `<gameId>:end` / `<gameId>:score:<h>-<a>` / `<gameId>:canceled` / `<gameId>:delayed` — 기존 `sent_log` 재사용, once-per-key.
- TTL **120~300초** (임박성 소멸 — 늦게 온 득점 알림은 무가치). Safari 2KB 페이로드 상한 준수.
- **조용한 시간 충돌**: 현재 `isQuietHour`(KST 22:00~08:00)가 발송 전체를 차단하는데 경기는 22시를 넘김 → 카테고리별 quiet-hour 정책으로 확장 필요: `game_live`는 **경기일 23:30까지 예외**(+사용자 야간 토글) 권장 (§5 결정 DL2). `ticket_open` 야간 예외 설계(BPP §4.4)와 동일 패턴.
- 분당 최대 발송량: 동시 5경기 × 전이 이벤트 — 득점 이벤트는 경기당 10~25회 발생 가능 → 구독자 많아지면 분당 수백 발송. Web Push 발송 자체는 무료·한도는 Worker CPU/요청뿐이라 여유. Chrome 2026-01 rate limit(분당 1,000/사이트)와도 거리 큼 — 단 **429 백오프**(시장조사 §10-3 보완항목 #1)를 이 단계에서 함께 구현.

## 3. 페이로드 설계 (LV2)

```json
{ "title": "한화 득점! 5:3", "body": "7회말 vs LG — 잠실", "tag": "live-<gameId>",
  "data": { "url": "https://minsubs.github.io/minsubsong/#home", "event": "score" } }
```
```json
{ "title": "우천취소 — 한화 vs LG", "body": "오늘 잠실 경기가 취소됐어요. 예매 취소/환불은 예매처 공지 확인",
  "tag": "live-<gameId>", "data": { "url": "https://minsubs.github.io/minsubsong/#home", "event": "canceled" } }
```
- `tag`를 경기 단위로 고정 → 같은 경기 알림은 OS 알림트레이에서 **최신 1개로 교체**(득점 알림 도배 방지, 추가 빈도 캡 없이 UX 해결).
- 시장조사 §10-3의 **DWP(Declarative Web Push) 호환 JSON**으로 처음부터 설계(iOS 18.4+ 순수 이득, SW 폴백 자동).
